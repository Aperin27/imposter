# Stage 4 contract

- Exactly 250 backend-only active pairs, the ten approved examples, permanent IDs, compatible answer types and a balanced eight-category editorial review. Freeze the original 18-ID index mapping; active existing round snapshots survive retirements.
- One `QuestionRotation` SQLite Durable Object at the fixed `imposter-global-question-rotation-v1` name per deployed Worker binding. A transaction atomically updates its shuffled remaining/used deck and permanent per-key allocation snapshot ledger. No per-room fallback deck.
- Validate host, connected membership, phase and three-player minimum before requesting a pair. Persist a room-instance UUID and pending start intent (`UUID:nextRound`) first. Allocate by RPC; clone and persist the started room/alarm before broadcasting. Retry the same intent after failure/restart; never recycle a reservation.
- Current clients include the observed round number in start actions to reject stale retries before allocation. The field remains optional for older already-open tabs; refresh those tabs to gain stale-request detection. An unversioned request after a reveal cannot be distinguished from an intentional next-round start.
- There is no transaction across the two objects. A crashed/unrecoverable start can reserve a question without displaying it. Treat reservations conservatively as consumed; never risk issuing that pair to another round in the same cycle. Room expiry does not touch the deck or ledger.
- Reconcile bank edits at allocation: remove retired pending IDs, shuffle additions into remaining available IDs, preserve used tombstones until cycle exhaustion. A retry uses its saved allocation even if retired later; it resumes an earlier reservation, not a fresh draw. Avoid last-ID repetition across boundaries when more than one ID is available.
- Store randomly reversed normal/imposter question order only in the new round snapshot. Existing snapshots never change orientation. Public serializer remains unchanged.
- Keep existing Room namespace/migration v1, append SQLite coordinator migration v2. Preserve UI, rate limits, credentials, reconnection, host succession, deadlines and hibernation. No dependencies, cloud access, Git mutations or publication.
- Verify pure deck/bank edits, 250 unique draws, cycles, cross-room concurrency, idempotency, room/coordinator eviction, service failures and reservation recovery; re-run all existing gameplay/UI tests, typecheck, production build and client-bundle privacy checks. Document finite free-plan quotas, ledger growth and singleton coordination limits.
